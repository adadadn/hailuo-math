# 考研数学 Viberecoding 产品 PRD v0.5

> 文档状态：方向已确认，待进入 MVP spec 评审。  
> 编写日期：2026-09-22  
> 产品代号：考研数学 Viberecoding

## 1. 文档目的

本 PRD 用于第一次梳理“部署在 Codex 中的考研数学 Viberecoding 产品”可能的产品形态、用户价值、功能边界和后续讨论问题。

当前不进入代码开发，不锁定最终技术方案。用户确认方向后，再将本 PRD 收敛为 MVP、里程碑和实现 spec。

## 2. 产品概述

### 2.1 一句话描述

一个部署在 Codex 工作环境中的考研数学学习与内容生产系统，围绕数学一、数学二、数学三、396 以及其他数学考试项目，帮助用户组织资料、拆解知识体系、生成和校验学习内容，并持续沉淀为可迭代的个人数学项目。

### 2.2 产品愿景

把分散的考研数学资料、题目、错题、笔记、计划和 AI 辅助能力，组织成一个可检索、可复习、可持续迭代的数学学习工作台。

### 2.3 产品定位

本产品不是单纯的聊天机器人，也不是只展示题库的刷题网站，而是“数学学习项目工作台”：

- 以不同考试项目为顶层组织方式
- 以知识点、题目、解法、错因和复习任务为核心对象
- 以 Codex/AI 为内容整理、分析、生成和校验助手
- 以本地文件和可追踪版本为长期资产

## 3. 目标用户

### 3.1 主要用户

1. 准备考研数学一、数学二、数学三的考生
2. 准备 396 经济类联考数学的考生
3. 需要管理多个考试项目或跨项目复用数学内容的用户

### 3.2 次要用户

1. 数学考研教师、辅导老师或课程内容整理者
2. 需要用 AI 批量整理题目、讲义、知识点的内容创作者
3. 希望搭建个人数学知识库和复习系统的长期学习者

### 3.3 用户前置条件

- 用户拥有一定的考研数学资料，可能以 PDF、图片、Markdown、Word、表格或手写笔记形式存在
- 用户愿意在 Codex 中通过文件、对话或命令操作项目
- 用户不一定具备编程能力，因此产品交互不能强依赖手写代码

## 4. 用户痛点与机会

### 4.1 主要痛点

- 数学一、二、三、396 的范围和难度不同，资料容易混在一起
- 题目、答案、解析、错题和知识点之间缺乏关联
- 学习计划常停留在表格或待办事项，不能反映真实掌握程度
- AI 可以生成内容，但容易出现公式、推理和答案错误，缺少校验与版本追踪
- 用户有大量资料，却难以快速回答“我哪里不会”“这道题考什么”“还应复习什么”
- 同一道题可能有多种解法，传统笔记难以结构化复用

### 4.2 产品机会

- 用考试项目、章节、知识点、题目和学习记录建立统一信息结构
- 利用 Codex 对本地资料进行整理、分析和增量维护
- 将 AI 生成结果与来源、推理过程、人工确认状态关联起来
- 用“学习任务 + 练习结果 + 错因”形成可持续更新的复习闭环

## 5. 产品范围的发散方向

以下方向均为候选，不代表第一版全部实现。

### 方向 A：考研数学知识库

管理考试项目、教材章节、知识点、公式、定理、典型题和资料来源，支持检索与关联。

### 方向 B：AI 题目解析与解法工作台

输入题目文本、图片或文件，生成解题思路、分步推导、知识点标签、难度判断和多种解法，并支持用户校验和修改。

### 方向 C：错题与薄弱点系统

记录做题结果、错误类型、错误原因、复习次数和掌握状态，自动生成薄弱知识点列表。

### 方向 D：个性化复习计划

根据考试项目、考试日期、每日可用时间、知识点掌握程度和错题情况，生成并调整复习计划。

### 方向 E：资料整理与内容生产

把 PDF、图片、讲义和笔记转换为结构化 Markdown/题目数据/知识点文档，形成可复用的个人内容资产。

### 方向 F：考研数学项目管理

允许用户同时维护数学一、数学二、数学三、396 和其他项目，各项目拥有独立范围、资料、计划和统计，同时支持公共知识点与题目复用。

### 方向 G：质量控制与数学正确性校验

对公式、推导、答案和题目元数据进行检查；对 AI 生成内容标记“待人工确认”，避免未经审核直接进入知识库。

## 6. 核心使用场景

### 场景 1：建立一个考试项目

用户选择“数学一”，系统展示或创建该项目的考试范围、章节结构、资料目录和学习状态。用户也可以创建“396 数学”或自定义其他项目。

### 场景 2：导入并整理资料

用户将讲义、题目、错题图片或 Markdown 文件放入项目目录，系统识别内容，提出分类、命名、标签和关联建议，由用户确认后入库。

### 场景 3：分析一道题

用户提供一道题，系统输出题目结构、考查知识点、解题思路、分步解答、易错点和可关联的相似题。用户可以编辑、确认或退回结果。

### 场景 4：记录一次做题结果

用户标记“正确、错误、不会、部分掌握”等状态，并补充错误原因。系统更新知识点掌握度和复习建议。

### 场景 5：查看当前薄弱点

用户查看按考试项目、章节和知识点聚合的薄弱点，进入对应错题、题目解析、公式和复习任务。

### 场景 6：生成复习任务

用户设定考试日期和可用时间，系统基于当前状态生成一组可执行任务，并允许用户调整和完成。

### 场景 7：审阅 AI 生成内容

用户查看 AI 生成内容的来源、状态和修改记录，将内容标记为“草稿、已审核、需修订、废弃”。

## 8. 功能需求候选

### 8.1 考试项目管理

- 创建、编辑、归档考试项目
- 配置项目名称、考试科目、考试范围和目标日期
- 为不同项目配置不同章节与知识点结构
- 区分项目独有内容和跨项目共享内容

### 8.2 资料与文件管理

- 按项目和资料类型组织本地文件
- 支持题目、讲义、公式、错题、笔记等基本分类
- 保存资料来源和导入时间
- 支持从文件生成结构化内容草稿
- 保留原始文件，不因 AI 整理覆盖原文

### 8.3 知识点体系

- 维护章节、知识点、前置知识和相关公式
- 为知识点关联题目、错题、资料和学习任务
- 支持用户自定义知识点
- 记录知识点的掌握状态和最近复习时间

### 8.4 题目与解析

- 创建或导入题目
- 记录题目来源、年份、题型、难度和适用项目
- 关联考查知识点
- 生成或编辑解题思路、详细步骤、答案和易错点
- 支持多种解法并标记推荐解法
- 支持人工审核状态

### 8.5 错题系统

- 记录错误题目及做题时间
- 记录错误类型：概念不清、计算错误、方法错误、审题错误、步骤遗漏等
- 支持添加个人复盘笔记
- 生成再次复习和重做任务
- 查看某个知识点下的错题聚合

### 8.6 学习计划与任务

- 创建阶段性计划和每日任务
- 根据项目、考试日期和可用时间生成建议计划
- 任务关联到知识点、题目或资料
- 支持完成、跳过、延期和调整
- 展示计划执行情况，但不以复杂数据看板为第一优先级

### 8.7 AI 助手

- 解释知识点和公式
- 分析题目与生成解题草稿
- 从资料中提取结构化内容
- 根据用户上下文回答问题
- 对生成内容提供来源、状态和人工确认入口
- 允许用户明确选择 AI 是“讲解、整理、生成、检查”中的哪一种模式

### 8.8 内容质量与版本管理

- 所有 AI 生成内容默认进入草稿状态
- 记录内容来源和修改历史
- 支持人工确认、退回和废弃
- 对公式和推导提供可疑项提示
- 重要内容变更可通过 Git 或文件版本回溯

## 9. 非功能需求候选

### 9.1 正确性

- 数学公式、符号和分步推导必须可读
- AI 输出不能默认视为正确，必须区分草稿与已审核内容
- 原始资料和用户确认内容不可被无提示覆盖

### 9.2 可追踪性

- 能知道一条内容来自哪个文件、哪次 AI 处理或哪次人工修改
- 重要变更可以回退

### 9.3 可扩展性

- 数学一、二、三、396 和其他项目不能写死在核心逻辑中
- 新增考试项目时尽量通过配置或数据完成，而不是修改大量代码

### 9.4 易用性

- 没有编程经验的用户也能完成导入资料、分析题目和记录错题
- 常用操作应优先支持文件和自然语言输入
- 内容结构要适合长期维护，不依赖一次性对话上下文

### 9.5 隐私与安全

- 默认优先使用本地项目文件保存学习资料
- API Key、个人资料和私密内容不能写入公开仓库
- 涉及外部模型时，需要明确哪些内容会离开本地环境

## 10. MVP 候选范围（待确认）

建议第一版先验证“资料进入系统后，能否形成可审核的题目/知识点资产”这一核心闭环，而不是同时实现完整课程、社交和复杂计划系统。

### MVP 可能包含

1. 创建和切换考试项目：数学一、数学二、数学三、396、自定义项目
2. 按项目管理本地资料文件
3. 导入一道题或一份题目资料
4. 生成题目结构、知识点标签和解析草稿
5. 人工编辑并确认内容
6. 将题目、知识点、解析和来源保存为结构化文件
7. 查看已确认内容并进行关键词检索
8. 初始化 Git，保留内容变更历史

### MVP 暂不建议包含

- 完整移动端 App
- 社区、排行榜和用户分享
- 复杂的自动排课算法
- 大规模在线题库运营
- 自动判卷和高可信数学证明系统
- 付费、会员和商业化体系
- 一开始就覆盖所有题型、全部教材和全部年份

### MVP 需要验证的致命卡点

- Codex 中的工作方式是否适合长期管理大量数学资料
- PDF、图片、Markdown 等输入能否稳定转成可用的结构化题目内容
- AI 生成的公式、推理和答案是否能达到“可人工快速审核”的程度
- 数学一、二、三、396 的差异能否通过项目配置表达，而不是复制四套系统
- 本地文件、索引和 Git 版本管理能否支持持续迭代

## 11. 成功指标候选

第一版不以用户规模作为主要指标，先关注核心闭环质量：

- 用户可以在 10 分钟内创建一个考试项目并导入第一份资料
- 一道题从导入到生成草稿、人工确认能够顺利完成
- 已确认题目可以被按项目、知识点和关键词检索
- 用户能清楚区分原始资料、AI 草稿和已审核内容
- 对同一份资料重复处理时，不会无提示地产生大量重复内容
- 用户能够通过 Git 或版本记录恢复重要内容

## 12. 明确不做的事情

本阶段不将以下内容视为已承诺需求：

- 不默认做成面向公众的商业化在线教育平台
- 不默认提供官方考试大纲或版权教材全文
- 不默认替代教师进行最终数学判断
- 不默认支持多人协作、组织管理和复杂权限
- 不默认把所有学习功能都做成图形化页面
- 不默认采用某个具体前端框架、数据库或模型服务

## 13. 待确认问题

以下问题会直接影响 MVP 和后续 spec，需要产品方向确认：

1. 第一优先用户是考生本人，还是教师/内容整理者？
2. 产品核心是“学习工作台”，还是“AI 数学内容生产工具”？
3. Codex 中的主要交互方式希望是什么：文件夹 + Markdown、Web 界面、命令行，还是混合方式？
4. 是否要求完全本地运行？是否允许调用外部大模型 API？
5. 第一版最想验证的是题目解析、资料整理、错题复习，还是计划管理？
6. 用户是否已有题库、讲义、错题等文件，需要优先兼容哪些格式？
7. “其他项目”是用户自定义考试项目，还是未来预设的其他考试类型？
8. 数学内容是否需要拍照/扫描识别？如果需要，图片公式识别将成为重要技术卡点。
9. 是否需要支持多人、教师批注或公开分享？
10. 是否有明确的考研目标年份、考试日期或使用周期？

## 15. 本轮确认的核心功能方向

本轮新增需求将产品主线进一步收敛为：

```text
选择考试项目 → 查看章节 → 完成每日一练 → 对答案/查看解析
→ 记录学习结果 → 每日打卡 → 根据历史表现生成下一次练习
```

这条链路可以作为 MVP 的核心闭环。

## 16. 每日一练

### 16.1 功能目标

用户进入系统后，首页默认展示“今日一练”，减少用户选择题目和制定当天任务的成本。

### 16.2 主要需求

- 用户可以选择当前学习项目：数学一、数学二、数学三、396 或自定义项目
- 系统根据用户当前项目、已学章节、历史答题结果、错题情况和近期练习记录生成每日题目
- 每日一练应显示题目数量、预计用时、覆盖章节和难度概览
- 用户可以开始、暂停、继续和提交当日练习
- 用户可以在当天结束前补做未完成题目
- 系统记录每日一练的生成时间、题目集合、完成状态和结果

### 16.3 生成策略的产品约束

每日一练不是完全随机抽题，至少应考虑：

1. 用户当前选择的考试项目
2. 用户已经学习或正在学习的章节
3. 近期错误率较高的知识点
4. 一段时间内尚未复习的知识点
5. 真题与模拟题的配比
6. 题目难度和预计用时
7. 避免短期内重复出现同一道题

第一版可以采用可解释的规则组合，不要求一开始就实现复杂推荐算法。系统需要让用户知道“为什么推荐这道题”。

## 17. 考试项目与章节结构

### 17.1 项目选择

系统首批支持：

- 数学一
- 数学二
- 数学三
- 396
- 自定义其他项目

### 17.2 章节层级

每个考试项目内部按较小粒度划分章节或知识模块，例如：

```text
考试项目
└── 一级章节
    └── 二级知识点
        ├── 真题
        ├── 章节模拟题
        ├── 错题
        └── 解析与公式
```

具体章节名称、覆盖范围和项目差异需要后续依据用户已有资料或确认过的考试范围建立，不能在当前 PRD 中直接假定为最终版本。

### 17.3 题目类型

- 真题：记录年份、来源、题号、适用项目和章节
- 章节模拟题：按章节组织，可记录难度、来源和版本
- 错题：由用户作答结果产生，也可以手动添加

同一道题可以关联多个知识点，但需要有一个主考查知识点，便于统计和推荐。

## 18. 对答案与解析

### 18.1 基本流程

```text
开始练习 → 查看题目 → 用户作答 → 提交答案
→ 查看正确答案 → 查看解析 → 标记掌握情况/错误原因
```

### 18.2 结果状态

每道题至少支持以下结果：

- 正确
- 错误
- 不会
- 部分正确
- 待确认

### 18.3 对答案要求

- 用户提交后可以查看标准答案
- 客观题优先支持自动判定
- 主观题或步骤题需要展示参考解法，并允许用户自评
- AI 判定的结果必须标记为“AI 判断”或“待人工确认”，不能伪装成确定事实
- 用户可以修改系统判定，并保留修改后的结果
- 对答案后可以直接进入错题记录和知识点复习

## 19. 打卡功能

### 19.1 打卡定义

每日一练完成、达到最低完成题数，或用户主动提交学习记录后，可以形成当天打卡。具体规则需要在 MVP 前确定。

### 19.2 基本功能

- 展示连续打卡天数和历史打卡日历
- 记录打卡日期、关联项目、完成题数和正确率
- 支持补充学习笔记或当天复盘
- 打卡不能替代真实答题记录，二者应分别保存
- 用户可以查看某段时间的完成趋势，但第一版不需要复杂数据大屏

### 19.3 拍照识别作答

用户可以拍摄或上传作答照片，系统尝试识别：

- 题目对应关系
- 用户填写的答案
- 可识别的计算结果或关键步骤
- 与标准答案的匹配情况

识别结果需要提供置信度和人工确认入口。识别失败时，用户仍可以手动选择正确、错误、不会或部分正确，不能阻塞打卡流程。

### 19.4 分阶段支持建议

- 第一阶段：支持上传照片、绑定题目、用户手动确认对错并完成打卡
- 第二阶段：支持客观题和简单填空题的答案识别
- 第三阶段：尝试识别主观解答步骤，并给出 AI 辅助判断

“拍照后自动判断复杂主观题全过程”不建议作为 MVP 的硬性验收项，因为手写公式、版面、裁切、印刷题目和推导步骤都会影响准确率。

## 20. 豆包 APP 接入边界

“可接入豆包 APP”需要拆成两个不同层次：

1. **调用豆包模型能力**：例如图片理解、文字识别或答案分析，属于模型/API 能力接入
2. **在豆包 APP 内直接运行或双向同步产品**：属于平台级产品接入，需要确认开放能力、账号体系、权限和审核要求

当前 PRD 只把第一层作为候选依赖，不把第二层视为已承诺能力。MVP 应先设计为产品自身能够完成上传、识别、确认和打卡；如果外部平台接入受限，核心学习闭环仍然可用。

## 21. 本轮建议的 MVP 核心闭环

建议 M1 先做以下范围：

1. 选择数学一、数学二、数学三或 396
2. 查看一个项目下的章节列表
3. 维护每个章节的真题和章节模拟题
4. 生成一组可解释的每日一练
5. 在线作答并查看答案/解析
6. 手动标记正确、错误、不会或部分正确
7. 生成错题记录和基础学习统计
8. 完成每日打卡
9. 支持上传作答照片，但先以人工确认结果为主

以下内容放到后续版本：

- 主观题手写步骤自动判分
- 高精度公式 OCR
- 完整的自适应推荐模型
- 豆包 APP 内嵌运行或账号级双向同步
- 社交、排行榜、教师协作和商业化功能

## 22. 需要你确认的产品决策

1. 每日一练默认每天几道题？是否允许用户自行调整题量？
2. 每日一练是否只从用户已学习章节出题，还是允许加入预习题？
3. 真题与模拟题在每日一练中的默认比例是什么？
4. “对答案”是否需要逐题显示详细解析，还是先只显示正确答案？
5. 打卡的最低条件是完成全部题目、完成指定题数，还是提交学习记录即可？
6. 拍照识别优先支持客观题、填空题，还是必须一开始支持解答题？
7. 你所说的“接入豆包 APP”具体是调用豆包能力，还是希望用户在豆包 APP 内直接使用本产品？
8. 题库和章节资料由你提供，还是需要系统第一步帮助生成？

## 23. 已确认产品决策

| 决策项 | 已确认内容 | 对 MVP 的影响 |
| --- | --- | --- |
| 每日一练题量 | 用户自行设定当天希望完成的题量 | 首页和每日一练创建流程需要提供题量设置；系统按该题量组卷 |
| 打卡条件 | 用户完成当天每日一练后自动打卡 | 打卡与每日练习完成状态联动；不以单独点击作为必要条件 |
| 豆包接入 | 调用豆包模型/API 能力 | 需要预留图片上传、服务端模型调用、结果展示和失败回退能力；不承诺在豆包 App 内运行 |

## 24. MVP 关键产品口径

### 24.1 “自动生成每日一练”的定义

MVP 中的“生成”定义为从已审核的真题和章节模拟题中，按照用户学习状态自动**组卷**，而不是由大模型临时编造一道新题。

这样可以确保每日题目存在可追溯来源、标准答案和解析，并使正确率、错题与推荐统计可信。AI 原创模拟题可作为后续版本能力，但必须经过审核后才可进入正式题库。

### 24.2 拍照识别的定义

MVP 使用豆包模型/API 对用户上传的作答照片进行辅助识别和分析。系统展示模型结果、置信提示和标准答案；用户可以确认或修改最终对错结果。

当模型调用失败、照片不清晰或结果不确定时，用户仍可以手动完成对答案和打卡，不能让外部模型成为学习流程的阻塞点。

## 25. 移动端产品决策

### 25.1 分阶段交付形态

产品采用逐步验证方式，不同时维护 PWA 和微信小程序两套前端。

- **M1**：手机优先的响应式 Web App，用户在手机浏览器打开 HTTPS 地址即可使用；可保留 PWA 安装入口。
- **M2**：在 Web App 上接入拍照上传与豆包模型/API 辅助分析。
- **M3**：在学习闭环已验证的基础上，开发并发布微信小程序客户端，复用已有后端、题库、组卷和学习记录能力。
- Codex 是开发工作区；用户在手机上访问的是部署后的产品网址或微信小程序，而非 Codex 本身。

### 25.2 移动端优先体验要求

- 首页第一屏直接进入“今日一练”，避免桌面端复杂导航。
- 单题作答、提交、查看解析和下一题必须适合单手操作。
- 题干、公式、选项和解析在窄屏上清晰换行，不能依赖横向滚动阅读。
- 拍照作答提供“拍照”和“从相册选择”两个入口。
- 图片上传、模型分析和结果确认在弱网络下展示明确状态并可重试。
- 每日题单、已完成作答和打卡结果在网络波动后不得丢失。

### 25.3 分阶段规划

- **M1**：响应式移动网页、项目/章节、每日一练、手动对答案、错题和自动打卡。
- **M2**：相机/相册上传、豆包图片分析、结果确认、离线缓存关键页面和当天题单。
- **M3**：微信小程序客户端、微信登录与平台发布流程。
- **M4**：章节掌握度、复习建议、题库批量导入、提醒和统计。
- **后续评估**：仅在小程序仍无法满足能力需求时，再评估原生 App 或跨平台壳应用。
